你这个 case 现在走到 无合理匹配，是现有流程优先级导致的，不是你看错：

1. 这次运行事件是
- 出子房间 厨房->客厅 @15471ms

2. 最近同类型标注是
- [3] 出子房间 @14867ms
- 偏差 15471 - 14867 = +604ms

3. 你的窗口是 500ms
- +604ms > 500ms，所以它不在可匹配窗口内。
- 代码先处理运行时事件匹配，这里直接走无匹配事件(运行时事件)，并暂停。
- 因为已经 return 了，这一轮不会再走后面的标注超窗扫描（漏匹配）。

所以你看到的是 无合理匹配，而不是 漏匹配。

如果你要这个场景归到 漏匹配，最小改法是：
- 在运行时无匹配分支里，先检查是否存在同类型、未匹配、且已超窗的标注事件；
- 若存在，就改走漏匹配文案（比如你这条就是 [3]）。

你这个问题非常关键，原因是这两点叠加：

1. 校验顺序是“先运行时事件，再漏匹配扫描”
当前逻辑等价于：

for (runtimeEvent in runtimeEvents) {
  if (异常) { pause; return }   // 这里直接 return
}
for (marked in markedEvents) {
  if (超窗) { 漏匹配; pause; break }
}

所以只要同一帧先命中了“运行时无合理匹配”，就会 return，后面的“漏匹配扫描”根本不执行。

2. 你这次阈值跨越点和回调点错开了
- 标注[3]时间：14867ms
- 窗口：500ms
- 漏匹配起点：15367ms
- 触发日志帧：15471ms（已经 +604ms）

如果在 15367~15471 之间没有单独一次“无运行时异常”的回调（可能因为解码/分析跳帧），那么第一次进入校验就直接走了“运行时无合理匹配”，漏匹配没机会报。
