# 04｜误检人体、准入锁定与实现交付说明

## 一、读完代码后的判断：保留现有锁定，再增加独立证据

当前工程并不是“YOLO 一出框就算人”，不应该推翻已经做过的规避。

审查范围包括：
`YoloAnalyzer.kt`、`YoloPoseAnalyzer.kt`、`SimpleTrackerEngine.kt`、`RemoteByteTrackEngine.kt`、`PoseData.kt`、当前 Presence 主实现及注册器、`VideoFeeder.kt`、`MainActivity.kt`、`PoseDrawer.kt`、设置页、房间模型及事件显示链。

`SimpleTrackerEngine` 的现有准入包括：历史最高置信度约 0.6、当前约 0.5、近期位置变化、双肩可信（约 0.7）、关键点完整度与上下位置约束。锁定后还有弱肩解锁、静止特征解锁、屏蔽/冷却等机制；未检测到时保留内部身份历史，而不是虚构新的检测位置。RemoteByteTrack 也保留应用侧的准入和屏蔽逻辑。

发现的不足：
- 有些骨架完整度检查只判断坐标非零，不充分检查关键点置信度。
- 框的抖动可以产生“运动”，不等于沙发纹理真的移动。
- 原始脚点的 0.00 阈值过于宽松，不适合作为新算法的强跨门证据。
- Detector ID 生命周期与真人的人数生命周期不能完全等价。

**结论：需要加强，但只在 V3 的新准入/几何层加强，既有跟踪器阈值和规则保持不变。** 旧算法可继续对照，避免一次同时改变所有层而无法解释结果。

## 二、V3 新人准入

V3 不允许未锁定的新目标直接增加人数。新人必须积累多个不同源时刻的可靠人体观测，默认至少 3 次、跨度至少 200ms，同时满足：
- 当前图像范围、框尺寸及关键点位置有效；
- 双肩置信度、躯干上下关系、可信上半身关键点数量通过检查；
- 有可信地面支持，没有明显框缩短、ROI 截断、身份冲突；
- 既有 Tracker 已锁定；
- 图像可用时，存在独立于 YOLO 框抖动的、多个人体空间格子的实际光流位移。

对完全静止图像，即使 YOLO 的框慢慢抖动，也不能仅凭检测坐标变化通过这层准入。没有图像时只能使用更保守的既有锁定＋多时刻解剖与地面位移检查，并显示降级信息；不能伪称仍完成了视觉验证。

本规则可能使开机时完全静坐、始终不动的人较晚进入自动准入。这与现有锁定策略一致的保守取向有关。已知开场人数可通过初始账本设置，不需要靠降低阈值把沙发误检也纳入。**新人的谨慎准入不意味着已确认的人一静止就要被删除。**

## 三、已有真人之后怎么维持

一旦通过准入，暂时掉检测、脚踝置信度下降、被家具挡住或既有 Tracker 暂时解锁，都不会立刻把账本人物删除。

同 ID 的大幅跳跃不能自动携带房间身份。新 ID 和旧遮挡对象匹配要满足位置、尺度、时间、一对一及匹配优势；多人竞争时待定。重新从某房间出来的人，在有明确来源时可以接续那个房间已有的匿名占用名额，避免同一人第二次出现又加一次总人数。

长时间存在的静态沙发误检仍可能骗过单一人体模型，因此本版没有宣称“必定零误检”。如果一个沙发结构在长时间内同时产生看似合理的姿态和一致图像运动，需要额外模型或明确负例标注才能进一步区分；不能用增加状态机层数代替观察信息。

## 四、学习的安全限制

持久化方向样本只来自可信足底实测跨门，进/出分开，按场景几何隔离；用于门比较时权重很小。通过遮挡猜出的事件不训练自身，未锁定目标不训练，镜头移动和身份冲突不训练。

没有实现神经网络在线训练，没有承诺只看三五次就掌握门的可见性。也不把“这间房账本里有人”当成“新检测一定从这间房出来”的唯一理由。

## 五、完整执行链

```text
源图像与真实源时间
  ├─ 有界灰度帧缓存（在 YOLO 背压之前）
  └─ 当前 YOLO26 Pose＋现有身份 Tracker
             ↓ 带成功/失败状态与 ROI 的时间对齐观测
     分格人体特征＋正反向光流＋有限反向回看
             ↓
     V3 人体准入与独立人数对象
             ↓
     可靠地面/门底边跨越，或严格接触下的遮挡推断
             ↓
     多门竞争、往返撤销、冲突待定
             ↓
     一次提交的来源→目标事件
             ↓
     全屋人数账本与不确定性显示
```

新的正式人数由 V3 独立计算。Legacy 没有被偷偷用于兜底改数；视觉失败时降级到保守地面判定，或保持待定。

## 六、代码组织

新包：`logic/roomalgorithm/flow/`

| 文件 | 职责 |
|---|---|
| `PortalV3Types.kt` | 几何、人体证据、可信脚点、事件与账本结果类型 |
| `PortalV3Core.kt` | 纯 Kotlin 准入、身份恢复、进出门、多门竞争、人数账本 |
| `PortalFrameHub.kt` | 独立源帧编号、源世代、ROI/成功状态、有界灰度缓存 |
| `PortalV3Vision.kt` | OpenCV 分格特征、正反向光流、背景验证、反向来源回看 |
| `PortalV3RoomAlgorithm.kt` | 统一接口适配、顺序喂帧、事件批处理、配置失效处理 |
| `PortalV3Overlay.kt` | 人体点、门底边、地面来源、待定状态、全屋人数显示 |
| `PortalV3Settings.kt` | 可选起始人数、按场景隔离的弱方向先验 |

对既有代码的修改限于注册新算法、元数据传递、源时间对齐、绘制入口、可选初值按钮、事件时间字段和资源清理。

没有修改 YOLO26 模型、LiteRT 推理参数、检测阈值、NMS、SimpleTracker/RemoteByteTrack 的内部锁定参数、手势判定或 `.Room` 文件格式。V3 独立使用严格地面观测，旧算法仍保留原始语义。

## 七、验证分层，不能把编译通过当视频准确率

交付验证包含：
- 纯核心回归测试：进入后仍可见、反向退出、家具掉检、门前消失不足、部分 ROI、误检未锁定、低置信骨架、静态图像框抖动、半身框、重复帧、探身返回、并排门、90° 客厅转角、身份恢复、匿名房间名额、异常图像与时间间断等。
- Android `:app:testDebugUnitTest` 与 `:app:assembleDebug`。
- APK 内模型与 arm64-v8a 资产检查。
- 没有连接设备时明确不宣称做过真机安装、目标手机性能验证或真实用户视频的准确率评估。

四份文档描述的是当前实现和限制。构建状态、测试数量、APK 大小与最终提交在交付回复和项目历史中记录，以最终实际结果为准。

## 八、实际使用

设置 → 房间算法 → **Portal V3 · 门线与人体光流（实验）**。保留已有客厅、门框、门底边及盲区配置。切换后从视频开头重播，不用新增门类型标记。

若知道视频开场人数，使用“V3 起始人数（可选）”设置对应视频的初值；不知道则保持未知模式，显示已知人数而不谎称空屋。

重点不是绿点越多越好，而是以下行为是否符合事实：沙发遮挡不转房、正面门已进入且仍可见时正确计入子房间、左侧近门证据不足时待定、并排/直角门不抢着猜、出来后不重复造人、真实跨门只记一次。

画面仍有旧 YOLO 框是正常的；它用于显示现有感知结果。V3 不读取 ViT/MIL 的矩形跟踪输出作为门事件证据。
